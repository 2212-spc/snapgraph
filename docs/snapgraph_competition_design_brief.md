# SnapGraph 参赛设计叙事简报

版本：2026-05-07 初稿
用途：发给资深设计者、产品设计导师、叙事顾问，请他们快速理解项目并给出故事建议。

---

## 1. 一句话先读懂

SnapGraph 是一个面向学生、科研者、产品经理和创作者的 **AI 认知记忆图谱**。

它不是为了帮用户保存更多资料，而是为了保存资料背后的思考现场：
用户当时为什么保存它、它关联哪个问题、支持了什么判断、留下了什么 open loop，以及未来如何重新找回这条思考路径。

当前最想打磨的核心叙事是：

> **AI 时代，答案越来越便宜，但人的判断来路越来越珍贵。SnapGraph 想保存的，不是资料本身，而是资料成为想法的那一刻。**

最新一版更锋利的叙事主轴：

> **答案越来越廉价，所以“为什么”必须越来越贵。**
> **我们的 AI 不假装是你。**
> **它把过去的你，完整地交还给现在的你。**

这版主轴把 SnapGraph 从“知识管理工具”提升为一个关于 AI 时代主体性的产品：

- 不是比谁的 AI 更自动，而是让 AI 更克制。
- 不是让 AI 替用户想，而是让用户重新听见自己曾经怎么想。
- 不是只找回资料，而是让过去的判断、灵感和 open loop 重新连接，帮助用户看见更完整的自己。

## 2. 比赛背景与评分要求

本项目准备参加 **2026 年中国高校计算机大赛 AIGC 创新赛 · 应用赛道初赛**。

初赛提交要求：

- 只需要提交一份作品策划书。
- 可提交 PPT、Word 或 PDF。
- 无需提交代码。
- 无需完成开发实现。
- 但策划材料需要体现产品原型、应用价值、大模型应用能力和完成度。

初赛评分重点：

| 维度 | 权重 | 对 SnapGraph 的启发 |
|---|---:|---|
| 作品创新性 | 40% | 必须讲清楚它不是普通知识库，而是“认知上下文 + 证据路径”的新范式。 |
| 应用价值 | 40% | 必须从真实用户痛点出发，说明高频、强需求、真实场景和社会价值。 |
| 作品完成度 | 20% | 初赛不要求代码，但材料要完整、丰满、呈现效果好。我们已有可跑 demo，可作为可信加分项。 |

复赛/决赛会增加“大模型应用能力”评分。虽然初赛主要看策划，但我们初稿就应该讲清楚：为什么这个产品没有大模型很难成立，以及大模型在其中不是装饰，而是核心工作流。

评分表中尤其关键的标准：

- 从用户真实需求出发，体现对使用者体验、情感或社会价值的关注。
- 作品理念清晰完整，贯穿于整个作品设计与实现。
- 功能具有原创性，突破传统思维或现有解决方案。
- 界面完整美观，易懂易操作。
- 交互流程自然，无断点。
- 通过交互方式解决某一痛点，或提供新颖操作体验。
- 技术可实现性较强，具备转化为实际产品、服务或应用的路径。
- 目标用户足够广泛，痛点足够明确，使用场景真实且高频。
- 有阐释大模型应用场景，并可通过 API 调用实现产品功能。

## 3. 设计思维课件中提取的方法要求

我们参考了两份设计思维课程材料：

- `6. 设计思维-思维发散与想法构建.pdf`
- `7. 设计思维-产品概念与叙事.pdf`

它们对本项目的启发如下。

### 3.1 从点子到概念

课件强调：功能点不是产品，概念才是产品。

一个弱表达是：

> 我们做了一个支持 Markdown、SQLite、RAG、graph.json 的知识管理系统。

一个更好的概念表达是：

> SnapGraph 是一个帮未来的你找回过去判断的 AI 认知记忆图谱。

课件里的判断标准：

- 能不能用“一个比喻 + 一群人”说清楚它是什么？
- 如果砍掉某个功能，产品概念还成立吗？
- 功能是否都服务同一个价值观？

SnapGraph 当前最有潜力的比喻：

- 记忆回执
- 思考现场
- 判断来路
- 认知副驾驶
- AI 认知记忆图谱

### 3.2 Feature vs Benefit

课件强调：用户不关心你做了什么，关心它能帮自己什么。

| Feature 功能说法 | Benefit 价值说法 |
|---|---|
| 支持图谱和 RAG 检索 | 未来不必记得精确关键词，也能找回当时的判断。 |
| 保存 Markdown wiki 和 graph.json | 让每一次保存都有可追溯的证据路径。 |
| 支持 LLM 摘要和问题生成 | 在资料刚被保存时，留下未来可召回的线索。 |
| 区分 user-stated 与 AI-inferred | AI 不会把猜测伪装成用户真实记忆。 |
| 本地保存原始资料 | 用户的知识和思考痕迹不被平台锁死。 |

### 3.3 黄金圈：从 Why 开始

不能从技术开始讲，要从信念开始讲。

当前 Why 草案：

> 我们相信，信息时代真正稀缺的不是资料，而是人对资料产生意义的那一刻。

进一步加深后的 Why：

> 在 AI 可以生成任何答案的时代，最珍贵的不是答案，而是“我为什么相信这个答案”的证据和来路。
> SnapGraph 想保护的，是人在信息洪流中形成判断的过程。

### 3.4 故事板三要素

课件要求故事板具有：

- Setting：谁，在什么真实场景中？
- Conflict：他遇到了什么冲突？
- Resolution：产品怎样介入，并造成情绪转变？

SnapGraph 的故事板不能只画 UI 截图，要画“用户失去思考线索”的那一刻。

推荐故事板主角：

> 小林，大三学生，正在做 AIGC 竞赛和论文开题。
> 他每天保存论文、网页、截图、产品案例和 AI 对话。两周后，他想继续推进项目，却只记得“我好像存过一个重要资料”，忘了它为什么重要、支持哪个判断、下一步要做什么。

核心冲突：

> 资料没有丢，但思考断了。

SnapGraph 介入：

> 当小林保存资料时，SnapGraph 生成一张“记忆回执”：原始资料、用户保存理由、AI 摘要、关联问题、未来召回问题、证据路径。两周后，他可以直接问：“我之前为什么觉得截图不是核心？”系统找回当时的原话、相关材料和图谱路径。

情绪转变：

> 从焦虑、混乱、记不起来，到“我重新站回了当时产生想法的现场”。

### 3.5 AI 的角色

课件提出 AI 可以是管家、伙伴、导师、工具人。SnapGraph 的 AI 最适合定义为：

> **认知副驾驶 Copilot**

它不是 Autopilot，不替用户决定“什么重要”。它帮助整理、连接、提醒和召回，但始终保留人的判断边界。

这个角色非常关键，因为 SnapGraph 的价值之一是负责任的大模型应用：

- 用户明确写下的保存理由标记为 `user-stated`。
- AI 推断出的理由标记为 `AI-inferred`。
- 找不到证据时返回低置信，而不是编造记忆。
- 回答必须附带证据来源和图谱路径。

### 3.6 Figure 1 应该是概念图，不是架构图

课件强调：第一张大图不能画成 `User -> API -> LLM -> Database`。

SnapGraph 的 Figure 1 应该画：

1. 场景锚点：深夜图书馆/宿舍，学生面对论文、截图、网页标签和竞赛材料。
2. 痛点特写：他皱眉问：“这篇我当时为什么觉得重要？”
3. 产品介入：SnapGraph 显示“记忆回执”和证据路径。
4. 情绪转变：他找回当时的判断，知道下一步该做什么。

Caption 草案：

> **保存资料的同时，保存它成为想法的那一刻。**

## 4. 用户与真实问题

### 4.1 目标用户

核心目标用户：

- 高校学生：做课程论文、竞赛、大创、毕设、保研科研。
- 科研入门者：阅读论文、整理文献、记录研究判断。
- 产品经理/设计师：收藏竞品、用户反馈、案例截图、会议记录。
- 内容创作者：保存灵感、素材、截图、文章、AI 对话。

共同特征：

- 每天保存大量信息。
- 项目周期跨天、跨周、跨月。
- 经常在多个主题之间切换。
- 不是找不到资料，而是忘了当时为什么保存。
- 未来的提问常常不是精确关键词，而是模糊回忆。

### 4.2 用户痛点

表层痛点：

- 收藏夹太乱。
- 笔记太多。
- 文件散落在微信、浏览器、网盘、Notion、截图相册和 AI 对话里。
- 找资料时不知道搜什么关键词。

深层痛点：

- 当时产生的灵感和判断没有被保存。
- 资料与项目、问题、任务之间的意义链条断裂。
- 用户重新打开资料时，只看到“是什么”，看不到“为什么当时重要”。
- AI 可以重新总结资料，但不一定知道用户当时真实意图。

一句话痛点：

> **资料还在，思考断了。**

更深的时代痛点：

> **AI 让答案变得廉价，却让判断的来路变得更需要被保护。**

### 4.3 高频场景

场景 1：学生做竞赛
用户保存论文、产品案例、评审标准、老师建议和 AI 对话。几天后要写策划书，却忘了某个材料为什么影响了方向判断。

场景 2：论文阅读
用户保存很多论文摘录。后续开题时需要回答“我为什么认为这个方法值得参考？”但传统文献管理器只告诉他论文标题和摘要。

场景 3：产品调研
产品经理收藏竞品截图、用户评论、市场分析。两周后复盘需求，想知道“当时为什么觉得这个交互值得借鉴？”

场景 4：创作灵感
创作者保存截图、短文、视频片段。创作时想找回“那种感觉”，但素材库只保存文件，不保存直觉。

## 5. SnapGraph 当前产品定义

### 5.1 产品定位

SnapGraph 是一个 Cognitive LLM Wiki：

- 原始资料不可篡改地保存。
- Wiki 页面由 AI 生成和维护。
- `index.md` 是内容地图。
- `log.md` 是操作日志。
- `graph.json` 和 SQLite 保存可查询的认知图谱。
- 答案可以写回 wiki，成为未来记忆的一部分。

它在 LLM Wiki 之上增加：

- Cognitive Context：为什么保存、关联项目、开放问题、未来召回问题。
- Source-to-thought links：资料与想法的连接。
- Evidence paths：回答必须有证据路径。
- Hybrid GraphRAG：关键词、图谱、可选 embedding、时间因素结合。
- Trust boundary：区分用户原话与 AI 推断。

### 5.2 产品的核心动作

当前最应该对外展示的用户流程：

```text
Drop material
-> Add why
-> Generate memory receipt
-> Connect to graph
-> Ask fuzzy recall question
-> See evidence path
-> Save useful answer back to wiki
```

中文产品流程：

```text
放入资料
-> 补一句为什么值得留下
-> 生成记忆回执
-> 连接到问题图谱
-> 未来模糊提问找回
-> 查看证据路径和下一步
-> 把有价值回答写回记忆
```

### 5.3 关键界面概念

1. 收集页
   用户拖入文件、截图、网页摘录或文字，补一句“当时为什么觉得它值得留下？”

2. 记忆回执
   保存后立即生成一张回执，包含：
   - 保存为：标题
   - 保存理由：用户原话或 AI 推断
   - 系统理解：摘要
   - 进入图谱：所属空间
   - 建议连接：相关项目/问题/任务
   - 开放问题：下一步要处理什么

3. 找回页
   用户不需要精确关键词，可以问：
   - 我之前为什么觉得截图不是核心？
   - 最近我围绕 SnapGraph 真正在追什么问题？
   - 哪些旧材料支持我对 AI memory 的判断？

4. 证据卡片
   回答不只是生成文本，而是展示：
   - 找回的用户原话
   - 相关材料
   - 连接路径
   - AI 探索回应
   - 涌现洞见
   - 下一步
   - 检索诊断

5. 图谱空间
   不是让用户先分类，而是材料进入后逐渐显出结构。空间可以代表项目、主题、研究问题或长期兴趣。

## 7. 大模型应用说明

### 7.1 为什么没有 AI 很难成立

传统方法失败的原因：

- 文件夹需要用户提前知道分类，但保存资料时，用户往往还不知道它最终会属于哪个问题。
- 标签系统依赖用户手动维护，长期成本高，很快失效。
- 关键词搜索要求用户记得准确词，但真实回忆常常是模糊的。
- 普通知识库只保存资料内容，不能主动提取开放问题和未来召回线索。
- 普通 AI 总结可以解释资料，却不一定尊重用户当时真实意图。

AI 的能力刚好补足：

- 从资料中生成摘要。
- 识别可能的项目/主题。
- 提取 open loop。
- 生成未来召回问题。
- 建议资料之间的连接。
- 根据模糊问题找回相关上下文。
- 综合材料回答，但保留证据路径。

### 7.2 AI 在 SnapGraph 中的具体任务

| 环节 | 大模型任务 | 价值 |
|---|---|---|
| 保存资料 | 摘要、关键细节提取 | 降低回看成本 |
| 写入原因 | 保留用户原话 | 建立最高置信线索 |
| 未写原因 | AI 推断可能保存原因 | 给未来召回一个低置信起点 |
| 建图 | 识别项目、任务、问题 | 生成认知图谱 |
| 召回 | 根据模糊问题检索上下文 | 不依赖精确关键词 |
| 回答 | 生成带证据路径的回答 | 避免空泛总结 |
| 审计 | 标记 user-stated / AI-inferred | 避免 AI 伪造用户意图 |

### 7.3 负责任 AI 边界

SnapGraph 的一个重要创新是：它不假装知道用户真实意图。

规则：

- 如果用户明确写了为什么保存，标为 `user-stated`。
- 如果系统推断为什么保存，标为 `AI-inferred`。
- 如果没有足够证据，返回低置信。
- 所有回答附带材料来源和图谱路径。
- AI 的角色是认知副驾驶，而不是自动驾驶。

这可以作为 AIGC 应用能力中的伦理与可信亮点。

## 8. 当前叙事草案

### 8.1 最重要的开场草案

> 我们正进入一个答案极其廉价的时代。
> 搜索能给资料，笔记能存摘录，大模型能立刻生成总结。
>
> 但一个更隐蔽的问题出现了：
> 当所有信息都能被保存、被总结、被再生成时，人反而更难记得，自己当时为什么被某条信息打动，为什么相信某个方向，为什么做出那个判断。
>
> 资料没有消失，消失的是资料成为“想法”的那一刻。
>
> SnapGraph 想保存的，正是这一刻。

### 8.1.1 发布会式主故事

这一版适合作为 PPT、路演口播和视觉叙事的最高层脚本。它不是逐字照念稿，而是节奏参考。

第一幕：那个深夜

> 凌晨两点。图书馆。一个叫小林的学生。
> 他面前的屏幕上，是三百条收藏。
> 他点开第一条，看了三秒，关掉。点开第二条，关掉。点开第三条，皱眉。
>
> 他不是没有资料。他有太多资料。
> 他只是想不起来：两周前那个保存了这一切的自己，当时到底在想什么。

第二幕：没人说出口的真相

> 我们这一代人，活在一个答案极其廉价的时代。
> 搜索能给资料，笔记能存摘录，大模型能立刻生成一份完整策划书。
>
> 什么都能给你。
> 但我们想问一个很多 AI 产品没有问的问题：
> **这一切之后，你自己还在吗？**

黑场定格：

> **资料还在。**
> **思考断了。**

第三幕：我们做了相反的事

> 我们没有做一个更聪明、更自动、更无感的 AI。
> 我们做了一个更克制的 AI。
>
> 两周后，小林问：我之前为什么觉得这个方向重要？
> SnapGraph 还给他的，不是 AI 总结，不是 AI 猜测，而是他两周前自己写下的那句话。
>
> 小林停了一下：
> **“对啊。我都忘了我写过这个。”**

这场戏的关键不是“AI 帮了他”，而是：

> **过去的他，在帮现在的他。**

第四幕：这件事叫什么

> 我们叫它：**思考回执**。
> 每一次保存资料，SnapGraph 都问一句：“你为什么觉得它值得留下？”
> 用户写下的那句话，会被原封不动地保存。未来再问起时，系统优先还给用户自己的原话。

立场页：

> **我们的 AI，不假装是你。**

设计规则：

- 用户写的话，标记为 `user-stated`。
- AI 推断的话，标记为 `AI-inferred`。
- 没证据时，承认不知道。
- 回答必须带来源和证据路径。

第五幕：更深的一件事

> 当 SnapGraph 使用久了，那些用户以为已经忘了的判断、以为不相关的资料、以为只是闪过的灵感，会开始彼此连接。
> 用户看见的不是一个更高效的资料库，而是一个更完整的自己。

第六幕：落幕

> 时间没办法倒流。
> 但你想过的一切，都可以等你。

### 8.2 更短的主张

> **让未来的你，重新站回当时产生想法的现场。**

备选：

> **保存资料成为想法的那一刻。**

备选：

> **不是帮你存更多资料，而是帮你保住判断的来路。**

新增更强候选：

> **在 AI 能造出所有答案的时代，让你记得自己是谁。**

注意：这句情绪很强，适合封面副标或结尾页，不适合所有页面反复使用。中间论证仍然要落回“思考回执、用户原话、证据路径、AI 边界”这些具体设计。

### 8.3 价值主张公式

> SnapGraph 帮助学生、科研者和创作者，通过 AI 认知上下文记录与证据图谱，解决“资料保存了但思考脉络丢失”的问题，并最终实现让每一次灵感、判断和开放问题都能被未来的自己重新找回。

### 8.4 乔布斯式概念发布表达

> 今天我们要做三件事。
> 第一，保存原始资料。
> 第二，保存当时的想法。
> 第三，保存资料和问题之间的证据路径。
>
> 资料库。笔记本。图谱助手。
>
> 你们明白了吗？这不是三个产品。
> 这是一个能找回过去判断的 AI 认知记忆图谱。
> 我们叫它 SnapGraph。

这个表达是否太像模仿乔布斯，需要设计者判断。它的优点是有记忆点，缺点是可能略显表演化。

### 8.5 产品概念层级

功能级：

> 我们做了一个支持资料保存和 AI 检索的知识库。

产品级：

> 我们做了一个帮学生和创作者找回过去判断的 AI 认知记忆图谱。

范式级：

> 我们提出一种 AI 认知留痕交互范式：每一次保存，不只是存档，而是生成一张可追溯的思考回执。

目前希望采用“产品级 + 范式级”的混合表达，避免过度学术化，也避免显得只是普通工具。

### 8.6 三层叙事骨架

最新建议采用“先立时代，再立立场，再许承诺”的三层结构。

第一层：时代命题

> **答案越来越廉价，所以“为什么”必须越来越贵。**

解释：这句话负责把项目从“笔记工具”拉到 AIGC 时代背景里。大模型让答案、摘要、内容生成变得廉价，但用户为什么相信、为什么在意、为什么行动，反而成为更稀缺的东西。

第二层：产品立场

> **我们的 AI 不假装是你。它只做一件事：把过去的你，完整地交还给现在的你。**

解释：这句话负责建立区别于其他 AI 产品的成熟度。许多 AIGC 产品强调“替你写、替你想、替你决定”。SnapGraph 反过来强调克制、边界、证据和用户原话。

第三层：价值承诺

> **当过去所有版本的你重新连起来，你会看见一个更完整的自己。**

解释：这句话负责把产品从“找回过去”推向“面向未来的生长”。SnapGraph 不只是怀旧式召回，而是让旧判断、旧资料、旧问题重新组合，帮助用户形成新的自我理解和下一步行动。

### 8.7 五个核心命题的定位

不要让一句话承担所有任务。不同句子服务不同页面和节奏。

| 命题 | 最适合位置 | 建议表达 |
|---|---|---|
| 时代命题 | 开场/S5/S7 | 答案越来越廉价，所以“为什么”必须越来越贵。 |
| 主体性立场 | S7/S9 | 我们的 AI 不假装是你。 |
| 核心交互 | S8 | 每一次保存，生成一张思考回执。 |
| Demo 记忆点 | S5 海报/S8 故事板 | “对啊。我都忘了我写过这个。” |
| 长期价值 | S9/S10/S13 | 过去所有版本的你连起来，成为更完整的你。 |

### 8.8 “涌现”能力的真实成熟度与讲法边界

这是一个战略问题：**“涌现”很有想象力，但必须诚实分层。**

当前真实成熟度判断：

- 已经可以展示：资料、保存理由、项目、open loop、future recall questions 之间的基础连接。
- 已经可以展示：图谱路径，如 `source -> triggered_thought -> project` 或 `source -> follow_up -> task`。
- 已经可以展示：项目簇、复查路径、认知缺口、低置信上下文等报告型 insight。
- 还不应夸大：系统目前还不能稳定发现“用户自己完全没意识到的跨项目深层新洞察”。
- 还不应夸大：`bridge_sources` 当前更多是信号计数和度数判断，不是真正强语义桥接。
- 还不应夸大：`high_value_review_paths` 目前主要由上下文字段生成，不是完全基于图算法验证出的复杂路径。

因此，比赛初稿中建议这样讲：

可以放在创新点里的事实：

> SnapGraph 已经能把资料、保存理由、开放问题和项目连接成可复查的证据路径，让用户看见旧材料之间的基础关联。

可以放在价值愿景里的表达：

> 随着材料积累，SnapGraph 将从“找回过去的判断”进一步走向“浮现跨材料的新洞察”，帮助用户看见一个更完整的自己。

不建议当前直接宣称：

> SnapGraph 已经能自动发现用户自己没意识到的深层洞察。

更稳妥的发布会表达：

> 一开始，它帮你找回过去的自己。
> 当资料慢慢变多，它开始帮你看见：过去那些不同时刻的自己，原来一直在讨论同一个问题。

这个说法既保留“涌现”的诗性，又不越过当前产品能力边界。

## 12. 当前最推荐的对外版本

如果只能给别人看一段，建议用这一版：

> 我们正进入一个答案极其廉价的时代。搜索能给资料，笔记能存摘录，大模型能立刻生成总结。
>
> 但一个更隐蔽的问题出现了：当所有信息都能被保存、被总结、被再生成时，人反而更难记得，自己当时为什么被某条信息打动，为什么相信某个方向，为什么做出那个判断。
>
> 资料没有消失，消失的是资料成为“想法”的那一刻。
>
> SnapGraph 是一个 AI 认知记忆图谱。它在用户保存论文、网页、截图或 AI 对话时，生成一张“思考回执”：保存理由、AI 摘要、关联问题、开放任务和证据路径。未来用户不必精确搜索关键词，只需要问“我之前为什么觉得这个方向重要？”，系统就能沿着材料和图谱找回当时的判断。
>
> SnapGraph 的 AI 不是替用户下判断的人，而是认知副驾驶。用户亲自写下的理由会被标记为 user-stated，AI 推断会被标记为 AI-inferred。找不到证据时，系统不会编造记忆。
>
> 我们想做的不是一个帮人存更多资料的工具，而是一个帮人保住判断来路的产品：让未来的你，重新站回当时产生想法的现场。

## 13. 附：项目内部真实信息摘要

项目当前名称：SnapGraph
项目类型：Cognitive LLM Wiki / AI 认知记忆图谱
当前技术基线：Markdown + SQLite + JSON graph + FastAPI + Vue + MockLLM / provider abstraction
当前设计原则：

- 原始资料可追溯。
- 用户原话优先。
- AI 推断必须标记。
- 没证据时不编造。
- 回答必须带证据来源和图谱路径。
- 图谱是导航和审计，不是炫技。
- 初期不做移动端、不做 Neo4j、不做 3D 图谱。

项目当前一句话：

> A local capture-to-connection space that preserves why something mattered when you saved it.

中文转译：

> 一个本地的“从保存到连接”的认知空间，帮助用户保留资料当时为什么重要。
